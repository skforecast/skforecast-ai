### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 10.7s

Prefer `ForecasterDirect` when the relationship between your inputs and the target seems to change across the forecast horizon, so that predicting near-term and far-term hours calls for different patterns. Otherwise start with `ForecasterRecursive`, the general-purpose default. Daily and weekly seasonality alone is not a reason to switch; the deciding factor is whether step-specific behavior matters for your horizon.

## When direct is a good fit

- **Step-specific relationships:** `ForecasterDirect` trains one independent model per step, so each horizon step can learn its own relationship with the inputs.
- **Avoiding error propagation:** a recursive forecaster feeds its own predictions back in as inputs for later steps. A direct forecaster uses only observed data for every step, so errors do not compound this way.
- **Long horizons:** the documentation describes direct as better suited to long horizons where patterns change per step.

## Trade-offs to weigh

- **Fixed horizon:** `steps` must be set when the forecaster is created. A recursive forecaster accepts any `steps` at predict time.
- **More models:** direct stores one estimator per step, which means more training time and memory. Training can be parallelized with `n_jobs`.
- **Simplicity:** recursive trains a single model and is the better default for short-to-medium horizons.
- **Intervals:** both strategies support bootstrapping and conformal prediction intervals, so uncertainty quantification does not favor either one.

## Why seasonality does not decide it

Both strategies work with lags, window features and exogenous variables, so either can represent daily and weekly patterns. Whether direct outperforms recursive on your series depends on your data, and I cannot say that from general documentation.

## How to get a starting point

Rank lags by partial autocorrelation with `calculate_lag_autocorrelation`, then keep those that exceed the asymptotic 95% white-noise band. This gives an informed starting point, not a final answer.

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

# Rank lags by |PACF| (n_lags=24 is an illustrative value, set it for your data)
lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

# Keep lags whose |PACF| exceeds the 95% white-noise band
threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```

## Reading the autocorrelation patterns

- If the PACF cuts off after lag *p*, lags 1 to *p* are the relevant ones.
- If the ACF shows peaks at lags *k*, *2k*, *3k*, the series likely has seasonality of period *k*, so lag *k* and its multiples are worth including.
- A strong trend can mask higher-lag structure. Read the ACF/PACF on the differenced series, or use `differentiation=1` in the forecaster.
- The confidence bands are pointwise, not joint tests. Some lags will cross them by chance, so treat them as candidates.
- `n_lags` for the PACF must be strictly less than half the series length.
