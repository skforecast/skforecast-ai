### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 16.5s

A direct forecasting strategy (`ForecasterDirect`) is preferable when the predictive relationship changes significantly across the forecast horizon, such as when predicting 1 hour ahead relies on different dynamics than predicting 24 hours ahead. It is also beneficial when you want to prevent error propagation over longer horizons, because each forecast step is modeled independently using only observed data rather than feeding prior predictions back as inputs. However, this approach requires fixing the forecast horizon at initialization and training a separate model for every step.

## When to prefer ForecasterDirect

* Horizon-dependent dynamics: In hourly demand, patterns at step 1 (immediate persistence) often differ structurally from patterns at step 12 or step 24 (peak-hour transitions). Direct models allow each step to learn distinct weights for the available historical lags.
* Mitigating error propagation: Recursive models use their own predictions as lagged inputs for subsequent steps, which can cause early forecasting errors to compound over long multi-step horizons. Direct models train separate estimators for each step, completely avoiding recursive feedback.
* Fixed forecast horizon: When your operational workflow always requires a fixed forecast window (for example, strictly 24 hours ahead for day-ahead planning), the requirement to fix `steps` at initialization is not a constraint.

## Trade-offs compared to ForecasterRecursive

* Training time and computation: Direct forecasting trains N separate models for an N-step horizon, which increases training time and memory usage compared to the single model used in `ForecasterRecursive`. Training can be accelerated across CPU cores using the `n_jobs` parameter.
* Horizon flexibility: `ForecasterRecursive` can predict any number of steps at prediction time, whereas `ForecasterDirect` can only predict up to the `steps` specified during forecaster initialization.
* Memory footprint: `ForecasterDirect` stores an estimator for each step in its `estimators_` dictionary, resulting in higher memory overhead.

## Identifying Lags with PACF

* Inspect the partial autocorrelation function (PACF) to find which past steps have a direct relationship with the target value after controlling for intermediate lags.
* Use `skforecast.stats.calculate_lag_autocorrelation` to rank lags by absolute partial autocorrelation.
* Select lags that exceed the white-noise significance threshold, or include specific seasonal multiples (for example, lag 7 for weekly cycles in daily data, or lag 24 for daily cycles in hourly data).

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

# Rank lags by partial autocorrelation
lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

# Keep lags exceeding the asymptotic 95% white-noise threshold
threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```
