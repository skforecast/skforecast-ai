### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 18.0s

Prefer a direct strategy (`ForecasterDirect`) when the relationship between your predictors and the target changes noticeably across the forecast horizon, for example when predicting one hour ahead needs different patterns than predicting a full day ahead. If you are unsure, the documentation recommends starting with `ForecasterRecursive` as the default. Strong daily and weekly seasonality alone is not a documented reason to switch.

## When direct is a good fit

- The predictive relationship is step-specific. Direct trains one independent model per step, so each horizon can learn its own relationship.
- You want to avoid error propagation. In a recursive forecaster, predictions feed into the next step. In a direct forecaster, each step uses only observed data.
- You can accept the extra cost. Direct trains one model per step and stores them all, so it uses more memory and trains more slowly. Training can be parallelized with `n_jobs`.

## When recursive is a good fit

- It is the default for most cases, especially short-to-medium horizons.
- It trains a single model and is faster and lighter on memory.
- The forecast horizon is flexible: `steps` is chosen at predict time, whereas `ForecasterDirect` requires `steps` at initialization.
- Both strategies support lags, window features (`RollingFeatures`), exogenous variables and prediction intervals, so either can encode seasonal structure.

### [probe] What is the best number of lags for my dataset?

- Skills: choosing-a-forecaster, autocorrelation-and-lag-selection; 9.1s

There is no single best number of lags, and I can't name one for your dataset because no dataset, forecast plan, or results were supplied with your question. What I can offer is a way to get an informed starting set of lags, which you then confirm with cross-validation.

## How to find a candidate set of lags

- Rank lags by partial autocorrelation with `calculate_lag_autocorrelation` from `skforecast.stats`. It returns a table ordered by absolute PACF.
- Keep the lags whose absolute PACF exceeds the asymptotic 95% white-noise band (1.96 divided by the square root of the training length).
- Read the ACF for seasonality. Peaks at multiples of a period k suggest including lags around k, 2k, and so on.
- If the series has a visible trend, read the ACF and PACF on the differenced series, or use the `differentiation` parameter in the forecaster.

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```

Here `n_lags=24` is only an illustrative value. `n_lags` must be strictly less than half the length of your series.

## Caveats

- The selected lags are an informed starting point, not a final answer.
- The confidence bands are pointwise, not joint tests. Some lags will cross the band by chance, so treat them as candidates.
- Use the PACF to judge autoregressive structure. The ACF is contaminated by indirect dependencies through earlier lags.
