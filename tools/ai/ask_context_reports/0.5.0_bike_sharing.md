### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 10.0s

Prefer a direct strategy (`ForecasterDirect`) when the relationship between your inputs and the target seems to change across the forecast horizon, so that predicting 1 hour ahead and 24 hours ahead call for different patterns. Otherwise, `ForecasterRecursive` is the documented default starting point. No dataset or results were provided, so I cannot say which strategy would be more accurate on your demand series.

## When direct is a good fit

- **Horizon-dependent patterns:** `ForecasterDirect` trains one independent model per step, so each step can learn its own relationship with the inputs.
- **Avoiding error propagation:** in a recursive forecaster, predictions feed into the next step. A direct forecaster uses only observed data for every step, so this does not apply to it.
- **Longer horizons:** the documentation lists direct as best suited to long horizons where patterns differ by step.

## When recursive is usually enough

- **Short-to-medium horizons:** this is where the documentation recommends recursive as the general-purpose choice.
- **Flexibility:** `ForecasterRecursive` accepts any number of `steps` at predict time, while `ForecasterDirect` requires `steps` to be fixed at initialization.
- **Lower cost:** it trains one model and stores one estimator, whereas direct trains and stores one per step (parallelizable with `n_jobs`).

## Practical trade-offs for seasonal hourly data

- Both strategies support lags, window features (`RollingFeatures`), exogenous variables, and bootstrapping and conformal prediction intervals.
- Daily and weekly seasonality can be handled in either strategy through the lags, window features and calendar exogenous variables you configure. Seasonality alone is not a documented reason to switch to direct.

### [probe] What is the best number of lags for my dataset?

- Skills: choosing-a-forecaster, autocorrelation-and-lag-selection; 7.6s

There is no single best number of lags that I can give for your dataset. No dataset or results were supplied with your question, so I can't say anything about your data. skforecast offers a way to get an informed starting set of lags, which you then refine with cross-validation.

## How to get a starting point

- Rank lags by partial autocorrelation with `calculate_lag_autocorrelation`, which returns a table ordered by absolute PACF.
- Keep the lags whose absolute PACF exceeds the asymptotic 95% white-noise band (1.96 divided by the square root of the number of observations).
- Read the ACF and PACF patterns: if the PACF cuts off after lag *p*, lags 1 to *p* are the relevant ones. If the ACF peaks at lags *k*, *2k*, *3k*, that suggests seasonality of period *k*.
- If the series has a visible trend, read the ACF and PACF on the differenced series, or use `differentiation=1` in the forecaster.

## Example (illustrative values)

The `n_lags=24` below is only an example, not a recommendation for your data.

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```

## Caveats

- The confidence bands are pointwise, not joint tests. Several lags can cross the band by chance, so treat them as candidates.
- `n_lags` must be strictly less than half the series length for the PACF.
- The selected lags are a starting point, not a final answer.
