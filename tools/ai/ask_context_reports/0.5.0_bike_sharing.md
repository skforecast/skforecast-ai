### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 10.6s

Start with a recursive strategy (`ForecasterRecursive`) and prefer a direct one (`ForecasterDirect`) when the relationship between your inputs and the target changes meaningfully across the forecast horizon, for example when predicting 1 hour ahead and 24 hours ahead calls for different patterns. Strong daily and weekly seasonality does not by itself favor direct. I can't say which will be more accurate on your demand data without a measured comparison.

## When direct is worth considering

- **Horizon-dependent patterns:** direct trains one independent model per step, so each step can learn its own relationship.
- **Error propagation:** a recursive forecaster feeds its own predictions back in as inputs for later steps. A direct forecaster uses only observed data for each step, so it avoids this.
- **Long horizons:** the documentation lists long horizons where patterns change per step as the best fit for direct. Recursive is described as best for most cases, especially short-to-medium horizons.

## Trade-offs of direct

- **Fixed horizon:** `steps` must be set when the forecaster is created. Recursive accepts any number of steps at predict time.
- **Cost:** it trains one model per step, so it is slower and uses more memory, because every estimator is stored. Training can be parallelized with `n_jobs`.
- **Features and intervals:** both strategies support lags, window features (`RollingFeatures`), exogenous variables, and bootstrapping and conformal intervals. Feature support is not a reason to pick one over the other.

## How to decide for your data

- **Measuring accuracy:** use `assistant.backtest()` to evaluate a candidate with realistic multi-step backtesting.
- **Choosing between strategies:** use `assistant.compare()` to put the recursive and direct candidates side by side on the same folds.
- **Reading the result:** a leaderboard reports which candidate scored better on the chosen metric, not why. Per-fold spread would be needed to judge whether a small margin is meaningful.

The documented approach is to build a candidate set from the autocorrelation structure of your series, then refine it with cross-validation.

## Step 1: Rank lags by partial autocorrelation

`calculate_lag_autocorrelation` returns a table of lags ordered by absolute PACF. Applying a significance band to it gives an informed starting set:

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation

lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)
```

Here `n_lags=24` is only an illustrative value. `n_lags` must be strictly less than half the series length.

## Step 2: Read the patterns

- If the PACF cuts off after lag *p*, lags 1 to *p* are the relevant ones.
- If the ACF peaks at lags *k*, *2k*, *3k*, the series has seasonality of period *k*, so include those seasonal lags.
- A slow decay across every lag suggests a trend. Read the ACF/PACF on the differenced series, or use `differentiation=1` in the forecaster.

## Step 3: Pass the lags to the forecaster

```python
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```

## Caveats

- The confidence bands are pointwise, not joint tests. Some lags will cross the band by chance, so treat them as candidates rather than proof.
- The selected lags are a starting point, not a final answer. I can't validate how well they will perform on your data.
