### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 10.3s

Prefer a direct strategy (`ForecasterDirect`) over a recursive strategy (`ForecasterRecursive`) when the relationship between features and demand changes substantially across the forecast horizon, such as when predicting 1 hour ahead relies on different patterns than predicting 24 hours ahead. A direct strategy is also advantageous over longer forecast horizons to avoid error propagation, as each step is predicted independently using only observed data rather than feeding intermediate forecasts back as inputs.

## When to Choose Direct Forecasting

* Horizon-dependent patterns: In hourly demand with strong daily and weekly seasonality, the dynamics governing immediate next-hour demand (such as short-term autocorrelation) often differ from those driving demand 12, 24, or 168 hours later (such as daily or weekly cycles). `ForecasterDirect` trains a dedicated estimator for each step, allowing each model to capture step-specific relationships.
* Preventing error accumulation: `ForecasterRecursive` uses predictions from earlier steps as inputs for future steps. Over multi-day hourly horizons, prediction errors can compound. `ForecasterDirect` trains independent models that condition only on observed historical values, eliminating recursive error propagation.

## Trade-offs and Practical Considerations

* Fixed forecast horizon: `ForecasterDirect` requires the `steps` parameter to be defined at initialization, fixing the prediction horizon. In contrast, `ForecasterRecursive` fits a single model that can forecast any number of steps at prediction time.
* Training time and memory: Because `ForecasterDirect` trains N separate estimators (where N is the number of forecast steps), it requires more memory and compute time than the single model trained by `ForecasterRecursive`. You can mitigate the training overhead by setting the `n_jobs` parameter to run estimators in parallel.
* Default recommendation: For short-to-medium horizons where error propagation is minor, `ForecasterRecursive` is generally the faster and simpler starting point. Move to `ForecasterDirect` if recursive forecasts degrade noticeably over the later hours of your horizon.

* Inspect the PACF for cutoff points, which highlight the most relevant autoregressive lags.

## Optimizing Lags with Cross-Validation

* Test candidate lag sets systematically using `bayesian_search_forecaster`, `grid_search_forecaster`, or `random_search_forecaster`.
* Compare candidates using backtesting to evaluate multi-step forecast accuracy across time folds.
* Prune redundant lags from your fitted model using `select_features`.

import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

# Rank lags by partial autocorrelation
lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

# Filter lags exceeding the white-noise threshold

    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
forecaster.fit(y=y_train)
