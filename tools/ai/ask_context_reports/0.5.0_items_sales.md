### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 9.8s

Start with a recursive strategy (`ForecasterRecursive`), and prefer a direct one (`ForecasterDirect`) when the predictive relationship seems to change across the forecast horizon. For example, predicting 1 hour ahead may need different relationships than predicting 24 hours ahead. Daily and weekly seasonality alone is not a reason to switch, and I cannot say which strategy will be more accurate on your demand data without measuring it.

## When direct is worth considering

- **Horizon-dependent patterns:** `ForecasterDirect` trains one independent model per step, so each step can learn its own relationship with the inputs.
- **Error propagation:** a recursive forecaster feeds its predictions back in as inputs for later steps, so errors can accumulate over a long horizon. A direct forecaster uses only observed data for every step.
- **Long horizons:** the documentation lists long horizons where patterns change per step as the best fit for direct. Recursive is the better fit for most cases, especially short-to-medium horizons.

## Trade-offs of direct

- **Fixed horizon:** `steps` must be set when the forecaster is created. A recursive forecaster accepts any number of steps at predict time.
- **More models:** one estimator is trained per step, so training is slower and memory use is higher. Training can be parallelized with `n_jobs`.
- **Same feature support:** both strategies support lags, window features, exogenous variables, differentiation and the same interval methods (bootstrapping and conformal).

## Why recursive is the default

- It trains one model, is fast, and works with any sklearn-compatible estimator.
- It is flexible about the forecast horizon.

## Get a starting set of lags

- Use `calculate_lag_autocorrelation` from `skforecast.stats` to rank lags by absolute partial autocorrelation.
- Keep the lags whose partial autocorrelation clears the white-noise confidence band, and pass them to the `lags` argument of your forecaster.
- Treat the result as an informed starting point, not a final answer.

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```

The `n_lags=24` here is only an example. `n_lags` must be strictly less than half the series length.

## Read the patterns

- If the PACF cuts off after lag p, lags 1 to p are the relevant ones.
- If the ACF peaks at lags k, 2k, 3k, the series has seasonality of period k, and those seasonal lags are worth including.
- A strong trend can mask structure at higher lags. In that case, read ACF/PACF on the differenced series, or use the `differentiation` parameter in the forecaster.
- The confidence bands are pointwise, so some lags will cross them by chance. Use them to spot candidates, not as formal tests.
