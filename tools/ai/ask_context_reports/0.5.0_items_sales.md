### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 12.4s

Start with a recursive strategy (`ForecasterRecursive`) and move to a direct one (`ForecasterDirect`) only when the predictive relationship appears to change across the forecast horizon, or when you want to avoid error propagation. Strong daily and weekly seasonality alone does not call for direct; it is a reason to choose lags and window features that capture those cycles in either approach.

## When direct is worth considering

- **Horizon-dependent patterns:** if predicting 1 hour ahead relies on different relationships than predicting 24 hours ahead, one model per step can fit each horizon separately.
- **Error propagation:** a recursive forecaster feeds its own predictions back in as inputs for later steps. A direct forecaster trains one independent model per step using only observed data, so this does not occur.
- **Long horizons:** the documentation lists direct as best for long horizons where patterns change per step.

## When recursive is the better default

- **Flexible horizon:** you can pass any `steps` at predict time, while `ForecasterDirect` fixes `steps` at initialization.
- **Cost:** it trains one model and stores one estimator. Direct trains one model per step, which is slower and uses more memory, though it can be parallelized with `n_jobs`.
- **Short-to-medium horizons:** the documentation lists recursive as best for most cases, especially these.
- **Feature support:** both strategies support lags, window features, exogenous variables, differentiation, and bootstrapping and conformal intervals, so you give up nothing on that front by starting recursive.

## Step 1: Get candidate lags from the PACF

- Use `calculate_lag_autocorrelation` from `skforecast.stats`. It ranks lags by absolute partial autocorrelation.
- A PACF that cuts off after lag *p* suggests lags 1 to *p* are the relevant ones.
- ACF peaks at lags *k*, *2k*, *3k* suggest seasonality of period *k*, so lag *k* and its multiples may be worth including.
- A strong trend can mask higher-lag structure. Consider reading the ACF/PACF on the differenced series, or use `differentiation=1` in the forecaster.

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

# n_lags=24 is only an illustrative value; choose one that suits your series
lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

# Keep lags whose |PACF| exceeds the asymptotic 95% white-noise band
threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```
