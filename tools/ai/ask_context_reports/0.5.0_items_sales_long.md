### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 17.7s

Prefer `ForecasterDirect` when the predictive relationship changes meaningfully across the forecast horizon, for example when predicting one hour ahead needs different patterns than predicting a full day ahead. Otherwise, `ForecasterRecursive` is the recommended default. Strong daily and weekly seasonality alone is not a documented reason to switch, and no results for your data are available here, so I can't say which would be more accurate for it.

## When direct is the better fit

- **Horizon-dependent patterns:** `ForecasterDirect` trains one independent model per step, so each step learns its own relationship with the inputs.
- **No error propagation:** Recursive forecasting feeds its own predictions back in as inputs for later steps. Direct uses only observed data for every step.
- **Long horizons:** The documentation describes direct as best for long horizons where patterns change per step, and recursive as best for most cases, especially short-to-medium horizons.

## Trade-offs to weigh

- **Number of models:** Recursive trains one model. Direct trains one per step, so it is slower and uses more memory (the estimators are stored in `estimators_`). Training can be parallelized with `n_jobs`.
- **Horizon flexibility:** Recursive accepts any `steps` at predict time. Direct requires `steps` at initialization, so the horizon is fixed up front.
- **Features and intervals:** Both support lags, window features, exogenous variables, differentiation, and both bootstrapping and conformal prediction intervals. You don't lose these capabilities by choosing either one.

## How to decide for your data

The choice is empirical. `assistant.backtest()` measures the accuracy of a configuration, and `assistant.compare()` helps choose between a recursive and a direct candidate on the same backtesting setup. Comparing them is the way to confirm whether the extra cost of direct pays off.

## How to get a starting set of lags

- Use `calculate_lag_autocorrelation` from `skforecast.stats` to rank lags by absolute partial autocorrelation.
- Keep lags whose absolute PACF exceeds the asymptotic 95% white-noise band (1.96 divided by the square root of the training length).
- Read the ACF for seasonality. Peaks at multiples of some period k suggest including lags around k, 2k, and so on.
- If the series has a visible trend, read the ACF and PACF on the differenced series, or use the forecaster's `differentiation` parameter.

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

# n_lags=24 is only an illustrative value; it must be below len(y_train) // 2
lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```

## Caveats

- The confidence bands are pointwise, not joint tests, so a few lags will cross the band by chance. Treat them as candidates.
- Use the PACF to choose AR-type lags and the ACF for MA structure and seasonality.
- The PACF requires `nlags` to be smaller than half the series length.
