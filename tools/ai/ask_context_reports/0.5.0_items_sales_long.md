### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 10.8s

Prefer a direct strategy (`ForecasterDirect`) when the relationship between your inputs and the target changes meaningfully across the forecast horizon, or when you want to avoid error propagation. Otherwise the documentation recommends starting with `ForecasterRecursive`. Strong daily and weekly seasonality alone does not settle the choice, and no results are available here to say which would perform better on your demand data.

## When direct is a good fit

- **Horizon-dependent patterns:** the relationship needed to predict a short lead time may differ from the one needed for a long lead time. Direct trains one independent model per step, so each step can learn its own relationship.
- **Error propagation:** a recursive forecaster feeds its own predictions back as inputs for later steps, so errors can accumulate. Direct uses only observed data for every step.
- **Long horizons:** the documentation lists long horizons where patterns change per step as the best case for direct.

## When recursive is a good fit

- **General purpose default:** one model, flexible `steps` at predict time, and it works well for most cases, especially short-to-medium horizons.
- **Lower cost:** direct trains one model per step and stores them all, so it uses more training time and memory (though it can be parallelized with `n_jobs`).
- **Fixed horizon:** `ForecasterDirect` requires `steps` at initialization, while the recursive forecaster accepts any number of steps at predict time.

## Trade-offs for your use case

- Both strategies support lags, window features (`RollingFeatures`), exogenous variables, and bootstrapping and conformal prediction intervals, so neither gives up those capabilities.
- Calendar features can be supplied as exogenous variables to either approach.
- Whether direct beats recursive depends on your data and horizon. I cannot validate that without backtest results, so treat the guidance above as general rather than a prediction for your series.

## How to decide empirically

If you want to settle it with evidence, `assistant.compare()` can rank candidate models, and `assistant.backtest()` can measure accuracy for a chosen one. Using the same backtesting setup for both strategies keeps the comparison fair. Per-fold spread would be needed to judge whether a small difference between them is meaningful.

## Step 1: get candidate lags from the data

`calculate_lag_autocorrelation` ranks lags by absolute partial autocorrelation. You can keep the lags whose PACF exceeds the asymptotic 95% white-noise band, then pass them to the forecaster. The values below (`n_lags=24`, `steps=12`) are illustrative, not recommendations for your data.

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```

## Step 2: read the patterns

- If the PACF cuts off after lag p, lags 1 to p are the relevant ones.
- If the ACF peaks at lags k, 2k, 3k, the series has seasonality of period k, so lag k is a candidate.
- If the ACF decays slowly at every lag, there may be a trend. Read the ACF/PACF on the differenced series, or use the `differentiation` parameter in the forecaster.

## Step 3: treat the result as a starting point

- The confidence bands are pointwise, not joint tests, so some lags will cross them by chance. Use them to spot candidates, not to formally prove a lag matters.
- PACF requires `nlags` to be smaller than half the series length, otherwise the function raises an error.
- Lags chosen from autocorrelation are an informed starting point, not a final answer.
