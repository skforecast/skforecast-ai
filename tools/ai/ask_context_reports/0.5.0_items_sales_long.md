### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 10.0s

Start with a recursive strategy (`ForecasterRecursive`) and prefer a direct one (`ForecasterDirect`) when the relationship between your inputs and the target seems to change across the forecast horizon. Strong daily and weekly seasonality does not by itself point to direct; the documentation ties the choice to horizon-dependent patterns, not to seasonality.

## When direct is the better fit

- **Horizon-dependent relationships:** for example, predicting 1 hour ahead and 24 hours ahead may need different relationships between predictors and demand. Direct trains one independent model per step, so each horizon can learn its own relationship.
- **Error propagation is a concern:** recursive forecasting feeds its own predictions back in as inputs for later steps, so errors can accumulate. Direct models use only observed data at each step.
- **Long horizons:** the documentation describes direct as best for long horizons where patterns change per step, while recursive suits most cases, especially short-to-medium horizons.

## When recursive is the better fit

- **It is the default starting point:** one model, flexible `steps` at predict time, and it supports lags, window features, exogenous variables, differentiation, and all the probabilistic prediction methods.
- **Compute and memory:** recursive trains one model. Direct trains one per step, stores them all, and is slower, though it can be parallelized with `n_jobs`.
- **Flexible horizon:** direct needs `steps` fixed at initialization, while recursive does not.

## Step 1: Get candidate lags from the PACF

`calculate_lag_autocorrelation` ranks lags by absolute partial autocorrelation. You can keep those that exceed the asymptotic 95% white-noise band:

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation

lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)
```

The `n_lags=24` value is only an example. `n_lags` must be strictly less than half the length of your series.

## Step 2: Read the patterns

- If the PACF cuts off after lag *p*, lags 1 to *p* are the relevant ones.
- If the ACF peaks at lags *k*, *2k*, *3k*, that suggests seasonality of period *k*, so include those lags.
- If there is a strong trend, it can mask higher-lag structure. Inspect the ACF/PACF on the differenced series, or use the `differentiation` parameter in the forecaster.
- The confidence bands are pointwise, so some lags will cross them by chance. Treat the result as candidates, not a formal test.

## Step 3: Validate with search

The selected lags are an informed starting point, not a final answer. To pick between lag sets, you can:
