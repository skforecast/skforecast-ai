### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 9.1s

You should prefer a direct strategy (`ForecasterDirect`) over a recursive one when the predictive relationship changes significantly across the forecast horizon, or when error accumulation over long multi-step rollouts degrades recursive accuracy. For hourly demand with strong daily and weekly cycles, direct forecasting is particularly beneficial when predicting specific future points (such as peak demand 12 or 24 hours ahead) requires different feature relationships than immediate next-hour steps. However, direct models require training a separate estimator for every step in the horizon, which increases training time and memory usage.

## When to Prefer Direct Forecasting

* Horizon-dependent dynamics: If the factors driving demand vary by lead time (for instance, the next hour depends heavily on recent momentum, while 24 hours ahead depends mostly on daily periodicity), a direct model allows each step to learn its own specialized parameters.
* Mitigating error propagation: Recursive models use their own predictions as lagged inputs for subsequent steps, which may lead to compounded prediction errors over 24-step or 168-step horizons. Direct models train independent models for each step and condition purely on observed history.
* Fixed forecasting horizons: If your operational workflow always produces forecasts for a predetermined horizon (such as a fixed 24-hour day-ahead schedule), setting a fixed `steps` parameter at initialization matches the operational requirement without needing horizon flexibility.

## Trade-offs to Consider

* Computational cost: `ForecasterDirect` fits N distinct estimators (where N is the number of steps), whereas `ForecasterRecursive` fits only one model. For a 168-hour (one-week) horizon, this means training 168 models, though fitting can be parallelized using the `n_jobs` argument.
* Memory usage: Storing multiple estimators in memory increases storage overhead compared to keeping a single recursive estimator.
* Horizon inflexibility: Unlike recursive forecasters, which can generate predictions for any arbitrary number of steps during prediction, direct forecasters can only predict up to the `steps` value declared when the forecaster is created.

## Inspecting Autocorrelation with PACF

* The Partial Autocorrelation Function (PACF) measures the direct correlation between the target series and each past lag, removing the influence of intervening lags.
* Lags where the partial autocorrelation exceeds the white-noise threshold (1.96 / sqrt(n)) represent strong initial candidates.
* You can rank and inspect lags using `calculate_lag_autocorrelation` from `skforecast.stats`:

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation

# Rank candidate lags by absolute PACF
lag_table = calculate_lag_autocorrelation(data=y, n_lags=24)

# Filter lags exceeding the 95% confidence threshold
threshold = 1.96 / np.sqrt(len(y))
selected_lags = (
    lag_table.loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)
```
