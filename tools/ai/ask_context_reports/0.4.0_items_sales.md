### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 20.8s

You should prefer a direct forecasting strategy over a recursive one when the predictive relationship changes significantly across the forecast horizon, or when recursive error accumulation degrades performance over longer forecast horizons. In direct forecasting, a separate estimator is trained for each future step using only observed historical data, preventing early-step errors from compounding into later steps. However, this comes at the cost of training multiple models and requiring a fixed horizon defined at initialization.

## Key Scenarios to Prefer Direct Forecasting

* Horizon-dependent patterns: If predicting 1 hour ahead relies on recent immediate momentum while predicting 24 or 168 hours ahead relies on daily or weekly periodic cycles, direct models allow each step to learn its own specific weights and feature relationships.
* Avoiding error propagation: Recursive forecasting feeds predicted values back as inputs for future steps. Over long hourly horizons (such as 24 to 168 steps), small prediction errors early in the horizon can accumulate and distort later predictions. Direct models avoid this by conditioning every step directly on observed history.
* Sufficient computational budget: Because direct forecasting fits N separate models (one for each step in the horizon), it requires more training time and memory than recursive forecasting. When training time is manageable or parallelization via `n_jobs` is available, the computational trade-off is often worthwhile.

## Trade-offs to Consider

* Fixed horizon requirement: `ForecasterDirect` requires setting `steps` during initialization. Unlike `ForecasterRecursive`, which can predict an arbitrary number of steps dynamically, a direct forecaster cannot predict beyond the pre-configured horizon without retraining.
* Resource usage: Training 24 models for a daily horizon or 168 models for a full weekly horizon requires significantly more memory and compute than the single model trained by `ForecasterRecursive`.

In skforecast, the best lag configuration depends on the autocorrelation structure and seasonality of your series. It is typically determined by analyzing partial autocorrelation values or by evaluating candidate sets through hyperparameter tuning.

## Methods for Selecting Lags

- Analyze the PACF: The partial autocorrelation function (PACF) measures the correlation between the series and each lag after controlling for shorter lags. Significant spikes in the PACF highlight candidate lags. You can compute and rank them using `calculate_lag_autocorrelation` from `skforecast.stats`.
- Hyperparameter search: You can define a grid or distribution of lag configurations and evaluate them via cross-validation using `bayesian_search_forecaster`, `grid_search_forecaster`, or `random_search_forecaster`.
- Feature selection: You can provide a broader initial set of lags and remove redundant ones using `select_features`.

## Example: Lag Selection with PACF

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

# Rank candidate lags by partial autocorrelation
lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

# Filter lags exceeding the asymptotic 95% confidence threshold
threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

# Configure the forecaster with the selected lags
forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```
