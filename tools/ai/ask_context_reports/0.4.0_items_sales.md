### [grounded] For hourly demand with strong daily and weekly seasonality, when should I prefer a direct forecasting strategy over a recursive one?

- Skills: choosing-a-forecaster; 8.8s

You should prefer a direct forecasting strategy when the predictive relationship changes significantly across the forecast horizon, such as when predicting 1 hour ahead relies on different dynamics than predicting 24 or 168 hours ahead. It is also preferable when error propagation from recursive multi-step forecasting degrades accuracy over longer horizons. However, this comes at the cost of training a separate model for each individual step.

## When to Prefer ForecasterDirect

* Horizon-dependent patterns: If the influence of past hourly lags or seasonal drivers shifts depending on how far out you are forecasting, `ForecasterDirect` trains an independent model per step to capture step-specific dynamics.
* Avoiding error propagation: In recursive forecasting, predicted values are fed back as inputs for future steps. Over daily or weekly horizons, any early prediction errors can compound. Direct models eliminate this because each step-specific model is trained directly on observed historical data.
* Fixed forecast horizons: When your application always requires a fixed horizon known at initialization (such as a 24-hour day-ahead forecast), the requirement to specify `steps` upfront is easily satisfied.

## Trade-offs and Considerations

* Computational cost: `ForecasterDirect` trains N separate estimators (one per horizon step) instead of a single model. This increases training time and memory usage, though models can be trained in parallel using `n_jobs`.
* Fixed horizon constraint: Unlike `ForecasterRecursive`, which can generate forecasts for any arbitrary number of steps at prediction time, `ForecasterDirect` requires the horizon to be declared at initialization.
* General recommendation: `ForecasterRecursive` is the standard starting point in skforecast for most single-series problems. Direct forecasting should be considered if validation shows that recursive error accumulation degrades performance over longer horizons.

## Identifying Candidate Lags with PACF

* The partial autocorrelation function (PACF) measures the correlation between the series and its previous values after removing the linear effects of intermediate lags.
* Use `calculate_lag_autocorrelation` from `skforecast.stats` to rank lags by absolute partial autocorrelation (`partial_autocorrelation_abs`).
* A standard practice is to retain lags that exceed the 95% white-noise confidence threshold, calculated as `1.96 / np.sqrt(len(y))`.

```python
import numpy as np
from skforecast.stats import calculate_lag_autocorrelation
from skforecast.recursive import ForecasterRecursive
from sklearn.ensemble import HistGradientBoostingRegressor

# Rank lags by |PACF|
lag_table = calculate_lag_autocorrelation(data=y_train, n_lags=24)

# Threshold against the asymptotic 95% white-noise band
threshold = 1.96 / np.sqrt(len(y_train))
selected_lags = (
    lag_table
    .loc[lag_table['partial_autocorrelation_abs'] > threshold, 'lag']
    .astype(int)
    .sort_values()
    .tolist()
)

# Initialize forecaster with selected lags
forecaster = ForecasterRecursive(
    estimator=HistGradientBoostingRegressor(random_state=963),
    lags=selected_lags,
)
```

## Refining the Lag Selection

* Selected lags from PACF analysis serve as a starting point; machine learning models often benefit from empirical validation across different combinations.
* Use `bayesian_search_forecaster` to test multiple lag configurations during hyperparameter optimization using backtesting folds.
* Use `select_features` to prune redundant or uninformative lags once your forecaster is configured.
