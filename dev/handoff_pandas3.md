## Objetivo y decisiones

- Plan completo en [roadmap-0.6.0.md](roadmap-0.6.0.md), sección
  "Compatibilidad con skforecast 0.28". D41: skforecast 0.28.0 y
  skforecast-ai 0.6.0 salen a la vez, sin 0.5.1. Pasos 1 y 2 hechos (#149,
  #150, #151: versión 0.6.0, `typer<0.29` en docs, mínimos de skforecast
  0.28 y Python 3.11).
- Paso 3 (este): suite en verde con pandas 2.3 **y** con pandas 3, los dos
  contra skforecast 0.28. Un solo PR a `0.6.x`, **un commit por causa**,
  y tras cada commit las dos suites completas. Orden acordado:
  0. Diagnóstico (hecho). 1. Copy-on-Write (hecho). 2. Fechas en
  microsegundos. 3. Texto como `str`. 4. `Pandas4Warning` de pandas 3.1.
  5. Tests atados a pandas 2. 6. Cierre: goldens, CI, nota de release.
- CI (cierre): añadir **un solo** trabajo con pandas 2.3 (Linux, Python
  3.11) en lugar de duplicar la matriz; el resto ya instala pandas 3.
- Los 53 goldens de contexto que fallan (`tests_llm/test_golden_context.py`
  y `test_describe.py`) son consecuencia de las causas 1 y 2: deberían
  volver a coincidir **sin regenerarlos**. Si alguno no, revisar antes de
  tocarlo.
- Forma de trabajar pedida por el autor: paso a paso y con calma; explicar
  cada paso antes de tocar nada y esperar su visto bueno. Commits y PR sin
  mención a Claude ni información confidencial (sin trailers, sin enlaces
  de sesión, sin "Generated by").

## Hecho

- **Paso 0, diagnóstico** (sin cambios). Con pandas 3.1.1 (la última),
  skforecast 0.28.0 (`d42a411`, punta de `0.28.x`), numpy 2.5.5, Python
  3.13: con `filterwarnings = error` tal cual, 111 ficheros de test no se
  recogen por `Pandas4Warning` en sus fixtures; con
  `-W "default::pandas.errors.Pandas4Warning"`, 339 failed, los mismos 339
  que en la revisión del 2026-11-24.
- **Paso 1, Copy-on-Write** (`a3a833b`): en
  [`_future_exog.py`](../skforecast_ai/_future_exog.py) la máscara
  `repeated` de fechas repetidas de las exógenas futuras se construye como
  array nuevo en vez de `&=` (el array de `to_numpy()` es de solo lectura
  en pandas 3). Las otras operaciones en sitio del módulo (líneas ~959,
  1301, 1343) son seguras: arrays nuevos o Series. Tests: los existentes
  (39 pasan ahora con pandas 3). Nota de release: pendiente, va en el
  cierre junto con el resto de pandas 3.

## Pendiente

1. **Paso 2, fechas en microsegundos** (propuesto, sin aprobar todavía).
   Medido: pandas 3 crea fechas en `us` en `to_datetime` de texto,
   `read_csv(parse_dates=...)`, `Timestamp(str)` y `date_range`; pandas 2.3
   en `ns`. `Timedelta.value` da ns en los dos (lo que usa `.value` está
   bien). [`profiling/data_profile.py`](../skforecast_ai/profiling/data_profile.py)
   hace aritmética entera en ns (`_DAY_NANOS`, `_HOUR_NANOS`,
   `offset.nanos`, `% day`); ya convierten con `as_unit("ns")` las líneas
   ~2637 y ~5758, el resto lee `.asi8` en la unidad que llegue. También las
   rejillas `pd.date_range(...).asi8` (~2870 y ~5810; en ~5810 se comparan
   con fechas ya en ns).
   Propuesta: un helper (p. ej. `nanoseconds(dates)`) que haga
   `as_unit("ns").asi8` con el mismo control de `OutOfBoundsDatetime` que
   la línea ~2637, usado en cada `.asi8` que entra en aritmética con ns y
   en las rejillas. No tocar `_dates.py:325` (solo ordena) ni el hash de
   `assistant.py:685`. Descartado: convertir a ns al cargar los datos (los
   DataFrames del usuario pueden traer `us` incluso con pandas 2.3, y
   cambiaría dtypes visibles). Primer paso: sacar la lista exacta de
   funciones afectadas desde los tests de fechas que fallan; luego
   `tests/tests_profiling/` con pandas 3, las dos suites y cuántos goldens
   vuelven a coincidir.
2. **Paso 3, texto como `str`**: `detect_categorical_exog`,
   `detect_numbers_as_text`, tipo del objetivo (`data_profile.py`) y el
   hash de `assistant.py` solo miran `is_object_dtype` (7 casos de
   `could not convert string to float: 'Cádiz'`, 8 scripts generados que
   fallan); ids de serie `str` en vez de `object`.
3. **Paso 4, `Pandas4Warning`**: `.dayofweek` (11 usos en
   `data_profile.py`, `_last_window.py`, `_utils.py`,
   `recommendation/calendar.py`, más 11 ficheros de tests y fixtures),
   `pd.infer_freq` que devuelve texto (5 usos; skforecast lo resuelve en
   `skforecast/utils/_pandas_compat.py::infer_freq` con
   `pd.option_context("future.infer_freq_returns_offset", True)`),
   `rename(inplace=...)` en un test. Los scripts generados no usan nada de
   esto (comprobado en `rendering/`).
4. **Paso 5**: 23 mensajes que ya no coinciden ("Regex pattern did not
   match": `pd.to_datetime` ya no dice "at position N"), un
   `FutureWarning` que pandas 3 no emite y dtypes `object` esperados.
5. **Cierre**: goldens, trabajo de CI con pandas 2.3, nota de release
   (`/release-note`), `/verify`, `/open-pr` a `0.6.x` (borrar este
   fichero antes).
6. Fuera de este PR, para el autor: avisar a skforecast
   (`REL-skforecast-ai-python311` de su roadmap). Después del paso 3 del
   plan vienen la sincronización de skills desde `0.28.x` (paso 4,
   `/sync-skforecast-assets` y check de pago) y los Candidatos.

## Entorno y verificación

skforecast 0.28.0 no está en PyPI: instalarlo desde git en los dos
entornos.

```bash
git fetch origin && git switch feature/pandas3
pip install "skforecast @ git+https://github.com/skforecast/skforecast@0.28.x"
pip install -e ".[test,llm,docs]" ruff
# segundo entorno, igual y además:
pip install "pandas>=3.1"
```

Comprobar:

```bash
ruff check skforecast_ai tests
python -m pytest -n auto -q -p no:cacheprovider                       # pandas 2.3
python -m pytest -n auto -q -p no:cacheprovider -rfE \
    -W "default::pandas.errors.Pandas4Warning"                         # pandas 3
```

Resultado al cerrar esta sesión (`a3a833b`): ruff limpio; pandas 2.3.3,
7106 passed, 1 skipped; pandas 3.1.1, 300 failed, 6805 passed, 2 skipped
(ningún fallo nuevo respecto al paso 0).
